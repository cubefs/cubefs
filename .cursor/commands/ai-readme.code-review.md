# /ai-readme.code-review - 智能代码评审

<mandatory_instruction>
**⚠️ 核心准则**：本命令的终点必须是生成完整的评审报告（Markdown 格式）。严禁在执行 Git 命令或读取文件后静默停止，必须完成后续的深度分析与报告输出。输出结果中必须显式包含代码评审报告的位置：`.codereview/cursor*review_temp*<随机数>.report.md`。

**❌ 禁止行为**：
- 禁止仅输出「评审清单」「检查清单」或基于 `code-review.mdc` 的静态列表。
- 禁止在未执行完整流程（步骤 1→2→3→4）的情况下，引导用户「指定评审范围」「回复要评审的范围」等；无参数时必须按默认行为（当前分支 vs 主干）执行并生成报告。
- 本命令的输出 = 基于 **Git diff** 的深度分析 + 按「评审报告模板」生成的完整报告文件，绝非清单或引导语。
</mandatory_instruction>

> 以只读方式对代码进行全面评审，输出结构化、可执行的评审报告。

## 命令格式

```bash
# 分支比较模式（默认）
/ai-readme.code-review [branchA] [branchB] [-p 需求文档路径] [-t 技术方案文档路径] [-b bug单文档路径]

# Commit 比较模式
/ai-readme.code-review -c [startRef] [endRef] [-p 需求文档路径] [-t 技术方案文档路径] [-b bug单文档路径]
```

### 参数说明

**分支比较模式（默认）**：

| 参数        | 类型             | 说明                            | 默认值          |
| ----------- | ---------------- | ------------------------------- | --------------- |
| `branchA`   | 位置参数（可选） | 源分支（主干分支）              | `origin/master` |
| `branchB`   | 位置参数（可选） | 目标分支（待评审分支）          | 当前本地分支    |
| `-p <path>` | 标志参数（可选） | 需求文档地址（PRD），本地或 URL | 无              |
| `-t <path>` | 标志参数（可选） | 技术方案文档地址，本地或 URL    | 无              |
| `-b <path>` | 标志参数（可选） | Bug 单文档地址，本地或 URL      | 无              |

<default_behavior_constraint>
> **强制规则（MUST）无参数调用时的默认行为**：直接对「当前分支」与检测到的「主干分支」生成 diff，并**最终生成一份完整的评审报告**。严禁仅输出 diff 内容、仅输出评审清单、或在生成 diff 后停止；必须完成步骤 2→3→4 的评审与报告输出流程。**禁止**向用户确认比较信息、询问分支名称或引导用户「指定评审范围」——无参数即按默认执行并产出报告。
</default_behavior_constraint>

**Commit 比较模式**（使用 `-c` 参数启用）：

| 参数         | 类型             | 说明                                    | 默认值       |
| ------------ | ---------------- | --------------------------------------- | ------------ |
| `-c`         | 标志参数（可选） | 启用同分支 Commit 比较模式              | 无           |
| `startRef`   | 位置参数（可选） | 起始 Commit 引用（hash/tag/HEAD~N 等）  | `HEAD~1`     |
| `endRef`     | 位置参数（可选） | 结束 Commit 引用                        | `HEAD`       |
| `-p <path>`  | 标志参数（可选） | 需求文档地址（PRD），本地或 URL         | 无           |
| `-t <path>`  | 标志参数（可选） | 技术方案文档地址，本地或 URL            | 无           |
| `-b <path>`  | 标志参数（可选） | Bug 单文档地址，本地或 URL              | 无           |

### 使用示例

```bash
# ============ 分支比较模式 ============

# 示例1：完整参数
/ai-readme.code-review feature/A personal/A -p docs/prd.md -t docs/tech.md

# 示例2：仅指定Bug单
/ai-readme.code-review -b bugs/issue.md feature/hotfix

# 示例3：混合使用URL和本地路径
/ai-readme.code-review -p https://wiki.com/prd -t docs/tech.md -b bugs/fix.md

# 示例4：使用默认参数（当前分支 vs origin/master）
/ai-readme.code-review

# ============ Commit 比较模式 ============

# 示例5：比较最近一次提交（HEAD~1 到 HEAD）
/ai-readme.code-review -c

# 示例6：比较最近5次提交
/ai-readme.code-review -c HEAD~5 HEAD

# 示例7：比较两个具体的 Commit Hash
/ai-readme.code-review -c abc1234 def5678

# 示例8：比较两个 Tag
/ai-readme.code-review -c v1.0.0 v1.1.0

# 示例9：比较指定 Commit 到 HEAD，并附带文档
/ai-readme.code-review -c abc1234 -p docs/prd.md -b bugs/issue.md

# 示例10：比较某次提交到当前（只指定起始点）
/ai-readme.code-review -c HEAD~10
```

## 执行流程

> 在执行过程中，请明确输出当前正在执行的步骤

### 步骤 1：参数提取

**解析规则（两遍扫描）**：

1. **第一遍**：提取所有标志参数（`-c`、`-p`、`-t`、`-b`）及其值
2. **第二遍**：剩余参数按顺序解析为位置参数
3. **模式判断**：
   - 如果存在 `-c` 参数，进入 **Commit 比较模式**，位置参数解析为 `startRef`、`endRef`
   - 否则进入 **分支比较模式**，位置参数解析为 `branchA`、`branchB`

**分支比较模式的默认值**：

- `branchA` 如未指定，使用 git 指令检测主干分支
- `branchB` 如未指定，执行 `git branch --show-current` 获取当前分支

**Commit 比较模式的默认值**：

- `startRef` 如未指定，默认为 `HEAD~1`
- `endRef` 如未指定，默认为 `HEAD`

**主干分支检测**（仅分支模式，当 `branchA` 未指定时）：

```bash
git symbolic-ref refs/remotes/origin/HEAD 2>/dev/null | sed 's@^refs/remotes/origin/@@'
# 如失败，按顺序尝试：main → master
```

### 步骤 2：生成差异

根据比较模式执行不同的差异生成逻辑。

**默认排除文件**：为减少噪音，diff 生成时自动排除以下文件类型：

| 类型 | 排除模式 |
| ---- | -------- |
| 文档文件 | `*.md`, `*.txt`, `*.rst` |
| 锁文件 | `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock` |
| 快照文件 | `*.snap`, `*.snapshot` |
| 压缩文件 | `*.min.js`, `*.min.css`, `*.map` |

---

#### 模式 A：分支比较模式（默认，无 `-c` 参数）

**差异对比逻辑**：

1. 使用 `git merge-base` 计算 `<branchA>` 与 `<branchB>` 的共同祖先，记为 `<baseCommit>`，即「对比基线」
2. 基于 `<baseCommit>` → `<branchB>` 的差异生成 diff 文件（忽略主干 `branchA` 自身历史中的无关变更）

按顺序执行以下命令（每个命令执行后检查结果）：

```bash
# 2.1 生成6位随机数（保存生成的6位随机数，用于后续步骤)
echo $((RANDOM % 900000 + 100000))

# 2.2 检查目录，如果没有.codereview目录就创建目录
mkdir -p .codereview

# 2.3 计算共同祖先（对比基线）
git merge-base <branchA> <branchB>

# 2.4 基于共同祖先生成 diff 文件（排除非代码文件）
git diff <baseCommit>...<branchB> \
  -- . \
  ':!*.md' ':!*.txt' ':!*.rst' \
  ':!package-lock.json' ':!pnpm-lock.yaml' ':!yarn.lock' \
  ':!*.snap' ':!*.snapshot' \
  ':!*.min.js' ':!*.min.css' ':!*.map' \
  > .codereview/cursor_review_temp_<随机数>.diff
```

---

#### 模式 B：Commit 比较模式（使用 `-c` 参数）

**差异对比逻辑**：

1. 直接比较 `<startRef>` 到 `<endRef>` 之间的所有变更
2. 适用于同分支内的 Commit 级别比较，无需计算共同祖先

按顺序执行以下命令（每个命令执行后检查结果）：

```bash
# 2.1 生成6位随机数（保存生成的6位随机数，用于后续步骤)
echo $((RANDOM % 900000 + 100000))

# 2.2 检查目录，如果没有.codereview目录就创建目录
mkdir -p .codereview

# 2.3 验证 Commit 引用有效性
git rev-parse --verify <startRef>
git rev-parse --verify <endRef>

# 2.4 获取 Commit 范围的简要日志（供评审参考）
git log --oneline <startRef>..<endRef>

# 2.5 生成 diff 文件（排除非代码文件）
git diff <startRef>..<endRef> \
  -- . \
  ':!*.md' ':!*.txt' ':!*.rst' \
  ':!package-lock.json' ':!pnpm-lock.yaml' ':!yarn.lock' \
  ':!*.snap' ':!*.snapshot' \
  ':!*.min.js' ':!*.min.css' ':!*.map' \
  > .codereview/cursor_review_temp_<随机数>.diff
```

> **注意**：
> - Commit 模式使用双点语法 `..` 而非三点语法 `...`
> - `':!pattern'` 是 Git pathspec 排除语法，用于过滤非代码文件

### 步骤 3：读取内容

- **步骤 3.1：读取 diff 文件**
  - 文件路径为：`当前工作目录\.codereview\cursor_review_temp_<随机数>.diff`
  - 使用步骤 2.1 中保存的随机数替换 `<随机数>`
  - 读取完整的 diff 内容进行分析
  - 如果文件不存在或读取失败，请报告错误："读取 diff 文件失败：<文件路径>"，并停止后续步骤
- **步骤 3.2：读取需求文档（如指定了 -p 参数）**
  - 如果是 URL（以 `http://` 或 `https://` 开头），尝试调用对应的 MCP 工具获取网页内容
  - 如果是本地路径，读取文件内容
  - 保存读取的内容为 `prdContent`
  - 如果读取失败，记录警告但继续执行："警告：读取需求文档失败：<路径>"
- **步骤 3.3：读取技术方案文档（如指定了 -t 参数）**
  - 如果是 URL（以 `http://` 或 `https://` 开头），尝试调用对应的 MCP 工具获取网页内容
  - 如果是本地路径，读取文件内容
  - 保存读取的内容为 `techContent`
  - 如果读取失败，记录警告但继续执行："警告：读取技术方案文档失败：<路径>"
- **步骤 3.4：读取 Bug 单文档（如指定了 -b 参数）**
  - 如果是 URL（以 `http://` 或 `https://` 开头），尝试调用对应的 MCP 工具获取网页内容
  - 如果是本地路径，读取文件内容
  - 保存读取的内容为 `bugContent`
  - 如果读取失败，记录警告但继续执行："警告：读取 Bug 单文档失败：<路径>"

<mandatory_step>
### 步骤 4：生成评审报告（强制要求）

**生成报告是本命令的核心目标。** 基于获取的差异内容（diff）和参考文档，按附录中的「评审维度」进行深度分析，并严格按照「评审报告模板」输出完整的报告。

> **注意**：即使没有提供需求文档（-p）、技术方案（-t）或 Bug 单（-b），也必须基于代码变更的质量、安全性、性能等维度生成完整的报告。严禁在读取 diff 内容后直接结束任务。
</mandatory_step>

### 评分标准

#### 评分公式（总分 10 分）

```
总分 = 正确性(3分) + 安全性(2分) + 性能(2分) + 可维护性(2分) + 测试(1分)
```

#### 各维度评分细则

| 维度         | 3 分                   | 2 分                     | 1 分         | 0 分         |
| ------------ | ---------------------- | ------------------------ | ------------ | ------------ |
| **正确性**   | 边界完善、异常处理完整 | 核心逻辑正确、存在小问题 | 有明显缺陷   | 核心逻辑错误 |
| **安全性**   | 全面防护、遵循最佳实践 | 基础防护、无高危漏洞     | 存在中危漏洞 | 存在高危漏洞 |
| **性能**     | 高效算法、合理缓存     | 无明显瓶颈               | 存在性能问题 | 严重性能问题 |
| **可维护性** | 结构清晰、文档完善     | 代码可读                 | 结构混乱     | 难以维护     |
| **测试**     | 覆盖全面、断言充分     | 基础测试覆盖             | 测试不足     | 无测试       |

### 质量等级

| 分数范围 | 等级    | 建议操作           |
| -------- | ------- | ------------------ |
| 9-10 分  | 🏆 优秀 | 可直接合并         |
| 7-8 分   | ✅ 良好 | 修复细节问题后合并 |
| 5-6 分   | ⚠️ 中等 | 需修复重要问题     |
| 3-4 分   | ❌ 较差 | 需大幅改进         |
| 1-2 分   | 🚨 很差 | 建议重写           |

### 严重度定义

| 级别     | 标识 | 定义                                 | 响应时间       |
| -------- | ---- | ------------------------------------ | -------------- |
| 必须修复 | 🔴   | 影响正确性、安全性、数据完整性的问题 | 合并前必须修复 |
| 建议修复 | 🟡   | 影响性能、可维护性的重要问题         | 本迭代内修复   |
| 细节建议 | 🟢   | 代码风格、微优化等细节问题           | 可择机修复     |
