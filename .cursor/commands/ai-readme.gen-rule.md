# 通用规则生成命令

这是一个通用的规则生成器。当用户提出任何需要转化为结构化规则的想法、需求或规范时，使用此命令自动生成符合 Cursor Rules 格式的规则文件。

## 核心理念

**从想法到规则**：将用户的任意想法（模糊或清晰）转化为可执行、可验证的结构化规则。

## 适用场景

- ✅ 代码规范和最佳实践
- ✅ 工作流程和操作指南
- ✅ 文档编写标准
- ✅ 设计规范和 UI/UX 准则
- ✅ 测试策略和质量标准
- ✅ 架构决策和技术选型
- ✅ 团队协作约定
- ✅ 任何需要规范化的领域

## 输入

### 必填
- **用户想法**：任何需要规范化的想法、需求或标准（可以是模糊的描述）

### 可选
- **目标范围**：规则适用的范围（文件类型、目录、场景等）
- **参考资料**：现有文档、代码示例、最佳实践链接
- **约束条件**：特殊要求、限制条件、必须遵守的原则
- **示例场景**：具体的使用场景或案例

## 工作流（必须按顺序执行）

### 1. 理解与提炼
- **必须**：提取用户想法的核心意图和目标
- **必须**：识别关键概念、约束条件和验收标准
- **必须**：列出所有不确定点，向用户澄清
- **应该**：识别用户想法所属的领域和相关理论基础

### 2. 结构化分析
- **必须**：将想法拆解为可独立描述的规则主题
- **必须**：为每个主题确定触发条件、适用范围和验证方式
- **应该**：识别规则之间的依赖关系和优先级
- **应该**：评估实施的可行性和潜在影响

### 3. 上下文调研（按需）
- **应该**：如果涉及代码库，扫描相关文件和目录结构
- **应该**：如果涉及现有规范，阅读相关文档和配置
- **应该**：收集支撑规则的事实证据（文件路径、代码片段、文档引用）
- **可选**：识别现状与理想状态的差距

### 4. 规则主题规划
- **必须**：确定需要生成的规则主题列表
- **必须**：为每个主题确定规则类型（Always Apply / Apply Intelligently / Apply to Specific Files / Apply Manually）
- **必须**：设计 `description` 和 `globs`（如适用）
- **应该**：考虑规则的可组合性和可扩展性

### 5. 生成规则内容
- **必须**：使用"必须/应该/可选"前缀明确强制程度
- **必须**：每条规则清晰、具体、可验证
- **必须**：禁止使用模糊词汇（"处理"、"优化"、"搞定"等）
- **应该**：提供具体示例或反例
- **应该**：为关键规则提供理论依据或最佳实践引用

### 6. 组织与输出
- **必须**：按照 MDC 格式生成规则文件
- **必须**：每个文件包含完整的 Frontmatter 和正文
- **应该**：按主题拆分为多个小文件（便于维护和复用）
- **应该**：提供清晰的章节结构和逻辑组织

### 7. 验证与自检
- **必须**：检查 Frontmatter 格式正确性
- **必须**：验证 globs 模式有效性（如适用）
- **必须**：确保规则可追溯（有依据或理由）
- **应该**：检查规则的完整性和一致性

## 规则生成准则

### 内容要求
- **必须**：规则清晰、具体、可验证
- **必须**：使用"必须/应该/可选"前缀
- **必须**：避免模糊表述和含糊动词
- **应该**：提供示例、反例或参考文件
- **应该**：每条规则独立成句，长度 ≤ 2 行

### 结构要求
- **必须**：单文件 ≤ 500 行
- **必须**：Frontmatter 在文件开头
- **必须**：Frontmatter 与正文之间有空行
- **应该**：按主题拆分 3-8 个文件
- **应该**：章节组织清晰、逻辑连贯

### 格式要求
- **必须**：文件保存到 `.cursor/rules/` 目录
- **必须**：文件扩展名为 `.mdc`
- **必须**：文件名使用 `kebab-case`
- **必须**：Frontmatter 仅包含：`description`、`globs`、`alwaysApply`

## 规则文件格式

### Frontmatter 规范

```yaml
---
description: 一句话描述规则触发场景（≤120 字）
globs: "文件匹配模式，多个用英文逗号分隔"
alwaysApply: true/false
---
```

**字段说明**：
- `description`：当类型为 Apply Intelligently 时必填
- `globs`：当类型为 Apply to Specific Files 时必填
- `alwaysApply`：必填，布尔值

### 规则类型

#### 1. Always Apply（总是应用）
任何时候都生效的全局规则。

```yaml
---
alwaysApply: true
---
```

**适用场景**：通用原则、全局约定、基础规范

#### 2. Apply Intelligently（智能应用）
AI 根据 `description` 智能判断是否使用。

```yaml
---
description: 当用户需要优化性能时使用此规则
alwaysApply: false
---
```

**适用场景**：特定场景的建议、上下文相关的最佳实践

#### 3. Apply to Specific Files（文件匹配）
根据文件路径匹配生效。

```yaml
---
globs: "src/**/*.ts, test/**/*.ts"
alwaysApply: false
---
```

**适用场景**：针对特定文件类型或目录的规范

#### 4. Apply Manually（手动触发）
仅在用户手动 @ 时生效。

```yaml
---
alwaysApply: false
---
```

**适用场景**：重构指南、迁移手册、高级策略

## 正文内容组织

### 灵活的章节结构
根据用户想法的特点，自主决定章节组织方式。可能包含但不限于：

- **核心原则**：基础理念和指导思想
- **具体规范**：详细的规则条目
- **示例演示**：正例、反例、代码片段
- **理论依据**：相关理论、最佳实践引用
- **实施建议**：如何应用规则的建议
- **常见问题**：FAQ 和注意事项
- **参考资料**：相关文档、文件路径

### 规则条目格式

```markdown
## 章节标题

- 必须：强制性要求，不得违反
- 应该：推荐做法，无特殊理由不应偏离
- 可选：可选做法，可按场景取舍
```

## globs 语法规则

### 基础语法
- `**`：匹配任意深度的目录
- `*`：匹配任意字符（不包括路径分隔符）
- `{a,b}`：匹配多个选项
- `!(pattern)`：排除匹配的模式

### 使用示例
```yaml
# 单个模式
globs: "src/**/*.ts"

# 多个扩展名
globs: "src/**/*.{ts,tsx,vue}"

# 多个模式（用逗号分隔）
globs: "src/**/*.ts, test/**/*.spec.ts"

# 排除特定目录
globs: "src/**/!(node_modules)/**/*.ts"
```

### 使用要求
- **必须**：根据实际情况编写 globs
- **必须**：多个模式用英文逗号分隔为单个字符串
- **必须**：确保至少能匹配到 1 个文件
- **应该**：优先使用具体的路径模式

用户可以用任何形式表达想法：
- ✅ "我想规范一下团队的 Git 提交信息"

### 命令执行流程

4. AI 按 MDC 格式生成规则文件

### 迭代优化
- 生成的规则可以根据反馈持续优化
- 可以请求添加更多示例或细节
- 可以调整规则的强制程度和适用范围
- 可以合并或拆分规则文件

## 术语定义

### Rule（规则）
单条可验证的规范陈述，使用"必须/应该/可选"前缀。

### Fact（事实）
支撑规则的客观依据，包含来源路径或引用。

### Evidence（证据）
为规则提供的最小充分代码片段、文档引用或理论依据。

### 强制程度
- **必须**（Must）：强制性要求，不得违反
- **应该**（Should）：推荐做法，无特殊理由不应偏离
- **可选**（May）：可选做法，可按场景取舍

## 核心原则

1. **从想法到规则**：将任意想法转化为可执行的规则
2. **灵活适应**：根据具体情况调整规则结构和内容
3. **明确验证**：每条规则都清晰、具体、可验证
4. **模块化组织**：拆分为多个小文件，便于维护和复用
5. **持续优化**：支持迭代改进和扩展
