部署与升级

读完本页可以回答：syncnode 和 dashboard 怎么部署到一个已经在跑 CubeFS 的 K8s 集群里，bench-mount RWM PVC 为什么必须先建好， 以及升级镜像时为什么必须走 OnDelete 串行手 delete——后者是反复踩坑的核心知识，新接手必读。

  • 部署方式cubefs-deploy（Terragrunt + OpenTofu）
  • 关键变量image · max_concurrent_tasks · bench_mount_pvc_name
  • 升级策略StatefulSet OnDelete（手动串行）
  • 面向读者SRE / 部署工程师

前置条件

  • CubeFS 主集群可用：master（3 主 raft）/ metanode / datanode 已经跑起来， curl http://<master>:17010/admin/getCluster 能正常返回 cluster 拓扑。
  • Consul 可达：syncnode、bench sidecar 都通过 Consul 上报心跳， consul_addr 必须和 master 用同一个，否则 master 看不到 syncnode。
  • K8s ≥ 1.24：syncnode 是 DaemonSet/StatefulSet， bench sidecar 是同 pod 的第二容器，依赖标准 PodSpec 没有特殊 CRD。
  • bench-mount 的 RWM PVC 已预备（生产 / test-hb 等需要跨节点共享 cfs 卷的场景必要——下面单独一节）。 如果只是 test-k3d 这种单节点验证场景，可以 bench_mount_pvc_name = "" 跳过。
  • Terragrunt ≥ 0.55 + OpenTofu ≥ 1.6 + kubectl：cubefs-deploy 用 Terragrunt 编排， kubectl 用来后续手动 delete pod 串行升级。

部署 syncnode

syncnode 以 cubefs 二进制 cfs-server -c sync.json（role=sync）启动，部署完全走 cubefs-deploy 仓库。 详细 IaC 入口见 cubefs-deploy 文档站 的 core / syncnode 章节。

对接触修改 IaC 的运维来说，需要关心的关键变量集中在 _envcommon/syncnode.hcl 和 envs/<env>/syncnode/terragrunt.hcl：

变量含义典型值
image syncnode 镜像 tag，必须与 master 镜像保持兼容（rc 字母+数字升级保持对齐） hub.../cubefs:v3.5.3.1.rc27
master_addrs master raft 三主地址，由 nodes.hcl 提供，不要手填 自动注入
consul_addr 同 master 共用，由 env.hcl 提供 自动注入
max_concurrent_tasks 单 syncnode 最多并行执行的任务数 生产 8 · 测试 1（强制串行验证）
transfers_per_task 单任务内的对象级并发（每个 shard 内） 4
bandwidth_limit_mbps 带宽上限（每 pod，0 = 不限） 0
bench_mount_pvc_name POSIX 压测用的 RWM PVC 名（" " 即关闭） cubefs-syncnode-bench / ""
bench_mount_storage_class 对应 PVC 的 SC（默认 cfs-sc） cfs-sc
gpfs_mounts hostPath 形式挂入 syncnode pod 的 GPFS / PFS 路径列表 [{ name, host_path }]
resources requests / limits。生产建议 4 CPU / 12 GiB，配合 fio libaio 高并发不会 OOM { cpu, memory }

首次部署最常用的命令（以 test-hb 为例）： 

# 1. 预览 diff（不会改集群）
make ENV=test-hb plan-syncnode

# 2. apply（不会自动滚 pod，见 OnDelete 升级 SOP）
make ENV=test-hb apply-syncnode

# 3. 看 daemonset 是否 9/9 Ready
kubectl -n storage-cfs get ds cubefs-syncnode

部署 dashboard

dashboard 是 Vue + Go 的运维 UI，自带 MySQL（独立于 master raft），通过 master REST 拿集群拓扑， 通过 Prometheus 代理拿测试时序，通过 syncnode REST 拿 sync / bench 任务详情。

  • IaC 入口：cubefs-deploy envs/<env>/dashboard/，模块 modules/cubefs-dashboard。
  • 关键变量：
    • image：dashboard 镜像 tag，独立版本号（如 v1.5.0.rc27），与 cubefs 镜像无强绑定。
    • master_addrs：master REST 入口（同 syncnode 共用 nodes.hcl）。
    • mysql_*：dashboard 自己的元数据库连接串。
    • prometheus_url：测试模块从这里查 fio / IOR 实时趋势。
  • Dashboard 升级没有 RWM 限制，可以用普通 RollingUpdate 直接 make ENV=<env> apply-dashboard。 镜像更新后 pod 会自动滚，无需手动 delete。

bench-mount RWM PVC 准备

POSIX 一致性测试（pjd-fstest）、并行元数据测试（IOR / mdtest）需要多个 syncnode pod 同时看到同一份 cfs 卷。 我们的做法是预先在 K8s 里创建一个 RWM（ReadWriteMany）PVC，再让每个 syncnode pod 都把它挂到固定路径 /cfs/posix-bench，bench sidecar 跑 fio / pjd-fstest 时直接读写这个路径。

典型 PVC 定义（cubefs-csi 提供动态供给）：

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: cubefs-syncnode-bench
  namespace: storage-cfs
spec:
  accessModes:
    - ReadWriteMany
  storageClassName: cfs-sc
  resources:
    requests:
      storage: 20Gi

在 envs/<env>/syncnode/terragrunt.hcl 里把这个 PVC 名字告诉模块，模块会自动把 /cfs/posix-bench 追加到 allowedRoots（bench sidecar 只允许在 allowedRoots 下读写）： 

inputs = {
  bench_mount_pvc_name      = "cubefs-syncnode-bench"
  bench_mount_storage_class = "cfs-sc"
  bench_mount_size          = "20Gi"
}

为什么这件事会强制 OnDelete：cubefs-csi 在多节点同时 NodeStage / NodeUnstage 同一个 RWM volume 时会出现 stale globalmount 撞车。如果 syncnode 走默认 RollingUpdate， 新 pod 一齐拉起 → 一齐 NodeStage 同一个 PVC → 9 个 pod 卡在 mount --bind exit status 32 全部 ContainerCreating。 因此 daemonset/statefulset 模板里恒为 strategy.type = OnDelete， wait_for_rollout = false，由人手逐个 delete 串行触发 CSI mount，把并发收敛掉。

test-k3d 例外：单节点环境无须共享 PVC，bench_mount_pvc_name = "" 跳过 RWM 挂载即可。 此时 daemonset 仍然是 OnDelete 策略，但因为单 pod 即时切换，看不出区别。

OnDelete 升级 SOP（必读）

触发条件：只要改了 syncnode 的 image / volumes / 任何 spec 字段，就要走这个流程。 resources 调整、gpfs_mounts 增减、bench_mount_* 切换都算。

三步操作

# 1) 改 IaC 并 apply（如升 _envcommon/images.hcl 里的 cubefs tag）
make ENV=<env> apply-syncnode
# apply 完 daemonset spec 已更新，但 N 个 pod 还跑老 spec（OnDelete 不自动滚）

# 2) 看 daemonset 模板符合预期（image / volumes 都对）
kubectl -n storage-cfs get ds cubefs-syncnode -o yaml | less

# 3) 逐个 delete pod，每个等 Ready 再 delete 下一个
for pod in $(kubectl -n storage-cfs get pods -l app=cubefs-syncnode -o name); do
  kubectl -n storage-cfs delete $pod
  node=$(kubectl -n storage-cfs get $pod -o jsonpath='{.spec.nodeName}' 2>/dev/null)
  until kubectl -n storage-cfs get pods -l app=cubefs-syncnode \
        --field-selector=spec.nodeName=$node --no-headers \
        | awk '{print $2}' | grep -q '^1/1$'; do sleep 5; done
done

绝对不要做

  • 不要 kubectl delete pods -l app=cubefs-syncnode --force。 一次性全删 → 新 pod 同时 NodeStage RWM PVC → CSI 撞车 → 9 个全卡 ContainerCreating， 只能去掉 bench-mount volume 引用、force delete 全部 pod 再走 OnDelete 串行加回——1 小时起步的恢复成本。
  • 不要把 strategy 改回 RollingUpdate，除非 cubefs-csi 已确认修复 RWM 并发 stage 问题。
  • 不要跳过手动 delete 步骤就声称升级完成。apply-syncnode 之后 pod 还在跑老镜像 / 老 spec， 需要逐个 delete 才会拉起新版本。
  • 不要在 delete 循环里并行 delete &。OnDelete 的全部意义就是串行收敛 CSI 并发。

常见故障排查

现象 1：新 pod 卡 ContainerCreating，event 里有 MountVolume.SetUp failed

检查是不是没按 OnDelete SOP 串行 delete。 kubectl -n storage-cfs describe pod <pod> | grep -A5 Events， 典型错误是 mount --bind ... exit status 32。 恢复路径：先 kubectl patch ds cubefs-syncnode --type=json -p='[...]' 临时去掉 bench-mount volume 引用， kubectl -n storage-cfs delete pod ... --force --grace-period=0 把卡住的 pod 全部清掉， 然后改回 IaC + apply-syncnode + 串行 delete。

现象 2：master 看不到 syncnode

curl http://<master>:17010/admin/getCluster | jq '.SyncNodes' 为空。检查：

  • syncnode pod log（kubectl -n storage-cfs logs <pod> -c cubefs-syncnode）有没有 consul register 失败。
  • env.hcl 里 consul_addr 是否与 master 同一个集群。
  • K8s 网络是否允许 syncnode → master:17010 / syncnode → consul:8500。

现象 3：syncnode pod OOMKilled

生产实测 4 GiB 默认 limits 在 fio libaio 高 iodepth × numjobs 场景会被 OOMKill。 在 envs/<env>/syncnode/terragrunt.hcl 增加 resources = { requests = { cpu = "2", memory = "6Gi" }, limits = { cpu = "4", memory = "12Gi" } }， 再走 OnDelete SOP 替换。

现象 4：bench 任务一直 pending / pending-shard

先看 kubectl -n storage-cfs get pods -l app=cubefs-syncnode 是否都 Ready； 再看 max_concurrent_tasks 是不是被压测场景调成 1（test-k3d 故意 1，正在排队是正常的）； 最后看 dashboard 「测试管理 / 任务」状态，里面有 master 派发失败的具体 reason。

现象 5：升级后 bench-mount 不见了

典型场景：bench_mount_pvc_name 从有值改为空，apply 后 daemonset 模板已去掉 volume， 但已运行的 pod 还挂着旧 mount。按 OnDelete SOP 逐个 delete 即可。反之亦然， 从空启用到指定 PVC 也必须走串行 delete 让 CSI 一次只 stage 一个节点。
