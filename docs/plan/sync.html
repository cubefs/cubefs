03 · Sync

同步：规则、任务、排障

CubeFS Sync 的核心是 SyncRule（规则 = 配置）与 SyncTask（任务 = 一次执行）。 读完本页可以回答：copy / move 怎么选；怎么写各种 backend 组合的 yaml；shard 与 parallelism 是两条独立的并发轴； 任务从触发到入库经过哪些状态；以及最常踩的 8 个坑分别怎么收。

  • 规则类型copy · move（mirror 演进中）
  • backendcfs · s3 · local（任意组合）
  • 并发轴ShardCount × Parallelism
  • 面向读者SyncRule 设计者 / 运维 / 排障值班

SyncRule 概念模型

一条 SyncRule 描述「从 src 到 dst，用什么策略、过滤器、并发度、校验强度，做哪一类操作」。 它是 声明，不是 动作——动作叫 SyncTask，由 trigger 或 schedule（cron）派发。 规则永远存在 master raft 上；任务由 master 入队、syncnode 领取并执行。

两种 type

type语义src 写入dst 写入典型场景
copy 把 src 拷到 dst，校验通过即停手；src 原样保留 只读 写 数据搬迁、跨集群灾备、归档落湖
move copy 完且 dst 校验通过 → 删除 src 对应 key（afterCopy=verify_then_delete_src） 校验后删除 写 清理冷数据、跨 backend 迁移老分区

move 的安全护栏：type=move 强制要求 checksumMode = strong（始终 sha256）， onExisting 只接受 "" 或 verify_then_skip；如果同时设了 confirm=true，必须先以 dryRun=true 跑一次预演（产出 would_* 事件），再以 dryRun=false + confirm=false 真删。 单一布尔位翻转就把演练变真删——这是被故意拒绝的设计。

三类 backend，6 种组合

src 和 dst 各自是一个 SyncEndpointConfig，目前支持 3 类 kind：

  • cfs：CubeFS 卷（vol + path）。走 CubeFS SDK 读写 metanode / datanode。
  • s3：任意 S3 兼容存储（火山 TOS / 阿里 OSS / MinIO / Ceph RGW）。endpoint / region / bucket / prefix，凭证可以走 accessKey/secretKey 内联或 accessKeyEnv/secretKeyEnv 间接。
  • local：syncnode pod 内的 POSIX 路径（hostPath / PVC / GPFS）。path 必须落在 allowedRoots 之下；可以调 bufferSizeKiB / directIO / fadviseSequential 优化大文件吞吐。

组合自由：cfs↔s3、s3↔s3、cfs↔cfs、local↔cfs、local↔s3、local↔local 全部支持，由 master 在 dispatch 时根据 src/dst kind 组合选 backend builder。 PreserveMode / PreserveOwner / PreserveXattr 三个 POSIX 元数据开关在跨 backend 时由 onMetadataUnsupported（warn / skip / error）收口。

配置示例

示例 1 · cfs → s3 归档（copy + 强校验）

id: archive-cfs-vol-to-tos
type: copy
schedule: ""              # 不开 cron，仅通过 dashboard / mcp trigger
src:
  kind: cfs
  vol: ai-training-2024
  path: /datasets/imagenet
dst:
  kind: s3
  endpoint: https://tos-s3-cn-beijing.volces.com
  region: cn-beijing
  bucket: cubefs-archive
  prefix: ai-training-2024/imagenet/
  storageClass: STANDARD_IA
  accessKeyEnv: TOS_AK
  secretKeyEnv: TOS_SK
filter:
  include: ["*.tar", "*.tfrecord"]
  exclude: ["*.tmp"]
  minSize: 1MB
parallelism: 16           # 单 shard 内 16 个对象并行
shardCount: 8             # 整体拆 8 个并行 shard（受在线 syncnode 上限收敛）
shardingStrategy: hash
checksumMode: strong      # sha256 src + 对比 dst checksum
onExisting: verify_then_skip
maxRetries: 3
resumeEnabled: true       # 断点续传（s3 multipart UploadID / cfs BytesDone）
bandwidthLimitMBps: 0
aggregateBandwidthLimitMBps: 800

示例 2 · s3 → s3 跨账号迁移（move + 演练）

id: migrate-cold-tier
type: move
src:
  kind: s3
  endpoint: https://oss-cn-shanghai.aliyuncs.com
  bucket: legacy-bucket
  prefix: 2023/
  accessKey: AKxxx        # 内联凭证（dashboard Approach C 推荐）
  secretKey: SKxxx
dst:
  kind: s3
  endpoint: https://tos-s3-cn-shanghai.volces.com
  bucket: new-bucket
  prefix: 2023/
  accessKeyEnv: NEW_AK
  secretKeyEnv: NEW_SK
shardingStrategy: prefix
shardPrefixes:            # 用前缀显式分区，分发到不同 syncnode
  - "2023/01/"
  - "2023/02/"
  - "2023/03/"
shardCount: 3
parallelism: 32
checksumMode: strong       # move 必须
afterCopy: verify_then_delete_src
onExisting: verify_then_skip
onSourceMutated: fail      # src 在拷贝过程中变了 → 这个 file 计 failed，绝不删 src
dryRun: true               # 第一次跑只生成 would_copy / would_delete_src 事件
maxRetries: 3

检查 dry-run 事件没有意外的 would_delete_src 之后，把 dryRun 改回 false 再 trigger 一次才真做删除。

示例 3 · local → cfs 从挂载点入仓（保留 POSIX 元数据）

id: ingest-gpfs-snapshot
type: copy
src:
  kind: local
  path: /mnt/pfs/snapshots/20260520
  bufferSizeKiB: 1024
  directIO: true
  fadviseSequential: true
  onSymlink: skip
dst:
  kind: cfs
  vol: data-lake
  path: /snapshots/20260520
filter:
  minSize: 0
  maxAge: 24h
parallelism: 24
shardCount: 4
preserveMode: true
preserveOwner: true
preserveXattr: true
onMetadataUnsupported: warn
checksumMode: size_etag
maxRetries: 5
resumeEnabled: true

示例 4 · 周期化（cron 触发）

id: nightly-snapshot
type: copy
schedule: "30 2 * * *"   # 每天 02:30 自动 trigger
src: { kind: cfs, vol: hot, path: / }
dst: { kind: cfs, vol: warm, path: / }
shardCount: 8
parallelism: 16
checksumMode: size_etag
onExisting: newer_only   # 类似 rclone --update，dst 比 src 新就跳过
maxRetries: 3

调度模型：ShardCount × Parallelism

这是两条独立的并发轴，搞混会导致要么没扇出、要么 OOM：

字段层级作用实际生效上限
shardCount master 拆分 一次 trigger 拆成 N 个并行 sub-task，分发到不同 syncnode hash 模式：min(N, 在线 syncnode 数)；prefix 模式：min(N, len(shardPrefixes))
parallelism 单 syncnode 内 单个 shard 内同时拷贝几个对象（worker pool） 受 syncnode 自身资源（resources.limits）约束
maxConcurrentTasks 单 syncnode 内 该 syncnode 同时领多少个 task（不限来源是哪个 rule） 由 syncnode 启动参数定义（生产默认 8，测试常压 1 验证排队）
bandwidthLimitMBps 每 pod 单 syncnode pod 的写带宽上限 0 = 不限
aggregateBandwidthLimitMBps 规则全局 所有 shard 加起来的总带宽上限 0 = 不限

三种 shardingStrategy

  • "" / hash（默认）：对每个对象 key 算 FNV-1a 哈希再取模，均匀分布。不要求 key 有意义。
  • prefix：算子明确写出 shardPrefixes，每个前缀一个 shard。适合按业务日期 / 客户 ID 自然分区的场景。
  • auto：master 在 trigger 时探针 src backend 的顶层前缀（cfs：mw 列目录；s3：ListObjects v2 with delimiter），命中缓存就按 prefix 拆，没命中回落到 hash。推荐 default，但 backend 必须能列前缀。

任务生命周期

+ 校验通过" --> done([done]) running -- "不可恢复错误" --> failed([failed]) running -- "用户 / mcp cancel" --> cancelled([cancelled]) failed -- "retry" --> queued cancelled -- "retry" --> queued classDef terminal fill:#f5f3ef,stroke:#cdc7bd,color:#221f1c; classDef live fill:#e8f0ff,stroke:#94aee0,color:#1d2c5a; class pending,queued,running live class done,failed,cancelled terminal
图 1 · SyncTask 状态机（master 视角）。running 内部的 per-file 子状态依次是 head src → list → copy → verify dst →（move 时）delete src；每步失败计入 FilesFailed / FilesSkipped，到达 maxRetries 之前都在 running 内自循环重试。

分片任务的聚合：master 用 sync_fanout 维护父任务的状态——所有 shard 全部 done 父才 done； 任意一个 shard failed 父也 failed（不会因为部分成功就糊弄上去）。 LastRunStatus 持久化到规则上，dashboard 看到的「最近一次状态」就是这里来的。

断点续传：resumeEnabled: true 时 syncnode 在本地 BoltDB 维护 InProgressStore。文件级别记 BytesDone（local / cfs）或 UploadID + parts（s3 multipart）。 syncnode 重启 → 领回原来的 task → 从断点继续，不会从头来过。这是 P2 修复的核心能力。

常用操作

三个入口，能力一致：

  • Dashboard UI「同步管理 / SyncRule」：图形化创建、trigger、pause / resume、看任务历史与失败明细。最适合一次性运维。
  • cubefs-mcp（LLM）：把下面这些操作包成 MCP tool（sync_rule_create / sync_rule_trigger / sync_task_list / sync_task_cancel / sync_task_retry / ...）。详见 05 · MCP。
  • master REST：所有底层 API 都暴露在 master 上，dashboard / mcp 只是封装。

直接打 master REST 的速查

# 列规则
curl -s http://<master>:17010/syncRule/list | jq

# 触发一次（同步入队，立即返回 task envelope）
curl -s -XPOST "http://<master>:17010/syncRule/trigger?id=archive-cfs-vol-to-tos"

# 暂停 / 恢复（cron 不再触发，已在跑的任务不受影响）
curl -s -XPOST "http://<master>:17010/syncRule/pause?id=..."
curl -s -XPOST "http://<master>:17010/syncRule/resume?id=..."

# 看正在跑 + 历史任务
curl -s "http://<master>:17010/syncTask/list?ruleID=...&status=running" | jq

# 取消单个任务（master 决定能不能取消，状态机不允许就拒绝）
curl -s -XPOST "http://<master>:17010/syncTask/cancel?id=<task-id>"

# 终态任务重试（failed / cancelled 才可以；running / queued 拒绝）
curl -s -XPOST "http://<master>:17010/syncTask/retry?id=<task-id>"

高频排障 · 8 条

1 · rule 创建失败：validation: ...

master 在写入前做了严格校验（type / backend kind / 凭证 / shardingStrategy / move 安全护栏全套）。 先看 master log 里的 reason，常见两类：(a) type=move 没显式 checksumMode=strong； (b) shardingStrategy=prefix 但 shardPrefixes 为空。

2 · 任务卡 pending / queued 不进 running

master 在等 syncnode 来领。三件事按顺序排查：

  • 有没有可用 syncnode：curl http://<master>:17010/syncNode/list。如果为空，syncnode 心跳没上来——回 02 · 部署 / 现象 2。
  • 所有在线 syncnode 是不是都被压满了（maxConcurrentTasks = 1 + 已有 1 个任务 + 队列还没空）。test-k3d 故意设 1，排队就是预期。
  • 任务是不是被 master 拒绝派发（某个 shard 的 shardPrefixes 没对应 backend 路径）。看 master log fanout dispatch 关键字。

3 · 任务一直 running 但 FilesDone 不涨

syncnode 在重试同一个文件。看 syncnode pod log： kubectl -n storage-cfs logs <pod> -c cubefs-syncnode | grep -E "retry|backoff"。 常见根因：dst backend 临时不可达（network / TLS）、src 文件被 holdered（locked）、s3 multipart UploadID 失效。 如果 maxRetries 不够，调高到 3-5；如果是 backend 真坏，先 cancel 任务、修好 backend 再 retry。

4 · move 任务执行后 src 没删干净

一定是 afterCopy != verify_then_delete_src 或 checksumMode != strong——executor 在双校验不通过时绝不删 src。 dry-run 跑一次，看 would_delete_src 列出来的对象数和你的预期是不是一致； 不一致就是过滤器 / 前缀写错了，要先修 rule 再跑。

5 · cfs↔s3 校验失败（dst checksum 对不上）

CubeFS 对象没有原生 ETag，s3 multipart 的 ETag 又是各 part MD5 再 hash，不能直接对 sha256。 executor 的做法：checksumMode=strong 时 src 边读边算 sha256，dst 校验回落到 Head 拿 size + 任意可获得的 checksum 头； s3 端必须确保桶策略允许 x-amz-meta-syncnode-sha256 透传，不然 Head 拿不到 dst checksum，executor 会把文件标 failed。 生产对接新 backend 时先用单文件 dry-run + 看 log 中的 verify reason。

6 · stale globalmount / mount 撞车（cfs backend）

syncnode 升级后大批量 stuck，根因是没走 OnDelete SOP。 回到 02 · 部署 / OnDelete SOP，串行 delete 每个 pod。 非升级场景如果偶现，可能是 cubefs-csi 自身的 stale，kubectl -n storage-cfs delete pod <syncnode pod> 单独触发一次重新 NodeStage 即可。

7 · POSIX 元数据迁移不全（mode/uid/gid/xattr 丢了）

检查 dst backend 是否声明 NativeModeWrite / NativeXattrWrite（s3 backend 是用 user-metadata 头模拟的，受 2 KiB 总额限制）。 onMetadataUnsupported 默认 warn——文件照样传，但元数据丢；改成 error 可以让任务在不能完整迁移时 fail，避免静默漂移。 local↔cfs / local↔local 的 mode / owner / xattr 都是原生写，没有缩水。

8 · onSourceMutated 误判

executor 在每个文件 copy 前后各做一次 Head 对比（size / mtime / etag）。 如果 src 在拷贝期间被 append（典型场景：日志正在写），onSourceMutated=fail 会让这个 file 计入 FilesFailed。 修正：activity-tail 类的 src 改用 filter.maxAge 排除最近 5 分钟内修改过的 key；或者改 onSourceMutated=skip 让 syncnode 安静跳过。 不要设成 retry——日志一直在写就一直 retry，会刷爆任务计数。
