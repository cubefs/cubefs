openapi: 3.0.3
info:
  title: CubeFS Syncnode — Complete Admin API
  version: "2.0.0"
  description: |
    Complete HTTP admin surface for the CubeFS sync subsystem.

    **Two servers, two surfaces:**

    | Server | Default Port | Surface |
    |--------|-------------|---------|
    | Master | 17010 | All sync management APIs: node registration, rule CRUD, task observability, direct dispatch |
    | Syncnode | 17911 | Local diagnostics only: version, stat, reload |

    **Authentication:**
    All master sync endpoints require `Authorization: Bearer <syncAdminToken>` (or
    `X-Sync-Token: <token>`). The token is configured as `syncAdminToken` in
    `master.json`. An empty value disables the check (dev/test mode).

    Syncnode local endpoints share the same token scheme but are only
    reachable on the node itself.

    **Response envelope (master + syncnode):**
    ```json
    { "code": 0, "msg": "OK", "data": <payload> }
    ```
    Non-zero `code` signals an error; `data` is null. HTTP status is
    always 200 — check `code` in the body.

    **Common error codes:**
    | code | meaning |
    |------|---------|
    | 0 | success |
    | 7 | ErrCodeParamError — missing or malformed param / body |
    | 10 | ErrCodePersistenceByRaft — raft submit failed; safe to retry |
    | 11 | ErrCodeInternalError — not found, conflict, or other server error |

  contact:
    name: CubeFS Sync Team

  /syncNode/dispatch:
    post:
      tags: [dispatch]
      summary: 直接下发任务（无需规则）
      description: |
        Dispatch a raw sync task without a pre-existing rule. Master picks
        the lowest-load available syncnode (or fans out across N nodes when
        `shardTotal > 1`) and forwards `OpSyncNodeRunTask` via the admin
        TCP channel.

        **Task ID constraints:**
        - Required; must not be empty.
        - Must not end with `/<digits>` — that suffix format is reserved
          for fan-out shard IDs synthesised by master. A caller that passes
          `"job/0"` would be indistinguishable from fan-out shard 0 of
          parent `"job"`, which breaks the terminal handler.
        - May contain other `/` separators freely (e.g. `"job/2026-05-14"`).

        **Single-node response:**
        ```json
        { "code": 0, "data": { "node": "10.89.6.10:17911", "taskID": "job-001" } }
        ```

        **Fan-out response (shardTotal > 1):**
        ```json
        { "code": 0, "data": {
            "taskID": "job-001",
            "shardTotal": 3,
            "owners": { "0": "10.89.6.10:17911", "1": "10.89.6.11:17911", "2": "10.89.6.12:17911" }
        }}
        ```
        Master retries dispatch up to 3 times with next-best candidates on
        nack/failure.
      operationId: dispatchSyncTask
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: "#/components/schemas/DispatchRequest"
      responses:
        "200":
          description: Dispatched — check `code` in body
          content:
            application/json:
              schema:
                oneOf:
                  - allOf:
                      - $ref: "#/components/schemas/Response"
                      - properties:
                          data:
                            $ref: "#/components/schemas/DispatchResponse"
                  - allOf:
                      - $ref: "#/components/schemas/Response"
                      - properties:
                          data:
                            $ref: "#/components/schemas/FanoutDispatchResponse"

  /syncNode/decommission:
    post:
      tags: [node-mgmt]
      summary: 下线 syncnode
      description: |
        State transitions:
        - `force=false` (default): mark the node `draining` and return.
          Cluster cron removes it when active task count drops to zero.
          Operator monitors via `GET /syncNode/tasks`.

          active task on the node, then raft-delete the node record.

        ```
        Active ──/decommission?force=false──→ Draining ──(tasks=0)──→ Removed
        ```

  /syncNode/response:
    post:
      tags: [node-registration]
      summary: "[内部] Syncnode 心跳 + 任务终态上报"
      description: |
        **Not for operator use.** Called by syncnode's heartbeat goroutine
        to push live metrics and task terminal reports to master.

        Master drives these state updates on receipt:
        - Heartbeat: updates `SyncNode.RunningTasks`, `BoltDBHealthy`, and
          other load-score inputs.
        - Task terminal: calls `SyncDispatcher.Release` + `SyncFailover.Forget`,
          updates the task ledger record to the terminal status.

        The response body carries master-computed bandwidth quotas
        (rule-level + backend-level) that syncnode applies immediately via
        its ratelimit registry. This inline quota delivery replaces the
        old `GET /syncNode/getQuota` poll (deprecated, removed).

        Response schema: `SyncNodeQuotaReply`.
      operationId: handleSyncNodeTaskResponse
      requestBody:
        required: true
        description: AdminTask envelope (serialised as JSON; same shape used for other node response endpoints)
        content:
          application/json:
            schema:
              type: object
      responses:
        "200":
          description: OK — quota assignments for this node
          content:
            application/json:
              schema:
                allOf:
                  - $ref: "#/components/schemas/Response"
                  - properties:
                      data:
                        $ref: "#/components/schemas/SyncNodeQuotaReply"
