cubefs-mcp（LLM 入口）

cubefs-mcp 是一个 stdio MCP 服务器，把 master 和 syncnode 的 admin REST API 封装成 34 个工具， 让 Claude Code / Cursor / Cline 等 LLM 客户端可以直接用自然语言操作 CubeFS 集群—— 列同步规则、触发 bench 任务、cordon syncnode 都不用再切 kubectl / 拷 curl。 读完本页可以回答：它有哪些工具、怎么 build、怎么注册到客户端、怎么验证连通性。

  • 形态单二进制 · stdio MCP server
  • 工具数34（6 大类）
  • 对接master REST + syncnode admin
  • 面向读者SRE / 平台开发 / 用 LLM 运维的人

是什么、为什么

cubefs-mcp 实现了 Model Context Protocol（MCP） 的 stdio 传输：客户端（Claude Code / Claude Desktop / Cursor / Cline ...）把它作为子进程拉起， 通过 stdin/stdout 交换 JSON-RPC 消息，每个 MCP「工具」对应一次 master 或 syncnode 的 REST 调用。

它解决一个很具体的问题——

  • 不想为了「列下 sync_rule」打开 kubectl + 找 master pod + port-forward + curl + 解 JSON
  • 不想把 admin API 直接暴露给 LLM（需要鉴权 / 端口转发 / 命名空间隔离）
  • 希望 LLM 看到的「能做什么」是有 schema、有描述、有 MUTATES/DESTRUCTIVE 标记的，而不是一堆 raw curl 模板

cubefs-mcp 把这三件事打包：进程本身在你自己的笔记本上跑（或同 K8s 集群的运维跳板上跑）， 通过 kubectl port-forward 拨入 master，然后向 LLM 暴露一组结构化工具。

工具速览（34 个，6 大类）

所有工具的描述、参数 schema、MUTATES / DESTRUCTIVE 标记都直接写在 Go 源码的 mcp.WithDescription 中， LLM 客户端通过 tools/list 拉到；下表只列「能干嘛」、对应 REST 路径，便于你查目录。 代码在 cmd/cubefs-mcp/internal/tools/，每个工具一个 *.go 文件，命名即工具名。

分类工具类型对应 master REST说明
cluster（4）pingRGET /admin/getClusterecho + 探活，5s 超时；第一道连通性检查
cluster_healthRGET /admin/getCluster返回完整 cluster 快照（master leader / 各 node 角色 / volume 摘要）
cluster_statRGET /cluster/stat容量、dp / mp / volume 数量、zone 汇总
versionR—返回 cubefs-mcp 自身的 version / commit / build_time
sync_rule（8）sync_rule_listRGET /syncRule/list可按 state（active / paused / degraded）过滤
sync_rule_getRGET /syncRule/get按 id 取完整 spec.SyncRule
sync_rule_createMPOST /syncRule/createbody 为完整 SyncRule JSON，master 走 spec 校验
sync_rule_updateMPOST /syncRule/update必须带 id；与 create 同 schema
sync_rule_deleteDPOST /syncRule/delete?id=仅删 rule，已派发的 task 继续
sync_rule_pauseMPOST /syncRule/pause?id=cron / on-event 触发暂停；已运行 task 不动
sync_rule_resumeMPOST /syncRule/resume?id=恢复触发
sync_rule_triggerMPOST /syncRule/trigger?id=立刻派发一次 task；paused rule 会被 master 拒绝
sync_task（6）sync_task_listRGET /syncTask/list支持 status / ruleID / owner 过滤
sync_task_getRGET /syncTask/get单 task 详情（src/dst/progress）
sync_task_exportRGET /syncTask/exportNDJSON 导出，since（RFC3339）按更新时间过滤
sync_task_cancelMPOST /syncTask/cancel取决于 task 状态，master 可能拒绝
sync_task_retryMPOST /syncTask/retry?id=仅终态（failed / cancelled）允许重试
sync_task_deleteDPOST /syncTask/delete?id=永久删 task 记录；运行中的 task 需先 cancel
bench_rule（6）bench_rule_listRGET /benchRule/list可按 id 过滤
bench_rule_getRGET /benchRule/get按 id 取完整 spec.BenchRule
bench_rule_createMPOST /benchRule/createbody 为完整 BenchRule JSON，master 拒绝未知字段
bench_rule_updateMPOST /benchRule/update必须带 id
bench_rule_deleteDPOST /benchRule/delete?id=仅删 rule
bench_rule_triggerMPOST /benchRule/trigger派发一次 bench_task（含 N 个 shard）
bench_task（5）bench_task_listRGET /benchTask/list支持 ruleID / status 过滤
bench_task_getRGET /benchTask/get含 status / progress / 各节点 stage 结果 / SLA 判定 / HDR buckets
bench_task_cancelMPOST /benchTask/cancel取决于状态
bench_task_retryMPOST /benchTask/retry?id=终态可重试
bench_task_deleteDPOST /benchTask/delete?id=需先 cancel 运行中 task
sync_node（5）sync_node_listRGET /syncNode/list当前 master 视角下健康的 syncnode 清单
sync_node_tasksRGET /syncNode/tasks看某 syncnode 上挂着的任务（含 status 过滤）
sync_node_drainMPOST /syncNode/drain?addr=停派新 task，现有 task 跑完；与 restore 配对
sync_node_restoreMPOST /syncNode/restore?addr=解除 drain
sync_node_decommissionDPOST /syncNode/decommission?addr=&force=从派发环里摘除；force=true 跳过运行中检查并孤立现有 task

类型列：R = read-only，M = MUTATES（改 master 状态），D = DESTRUCTIVE（不可逆）。 MCP 客户端会把这些标记展示给用户，destructive 工具默认需要二次确认；如果你给 LLM 写 prompt，建议显式说「使用 D 类工具前先 list/get 确认」。

部署：build 二进制 + 装 wrapper

cubefs-mcp 是 cubefs 仓库里的一个子命令，没有独立发布物——自己 build 即可。需要 Go 1.21+。 

# 1. 编译（在 cubefs 根目录）
go build -o ~/.local/libexec/cubefs-mcp \
  -ldflags "-X main.version=v0.1.0 \
            -X main.commit=$(git rev-parse --short HEAD) \
            -X main.buildTime=$(date -u +%Y-%m-%dT%H:%M:%SZ)" \
  ./cmd/cubefs-mcp

# 2. 装 wrapper（自动 port-forward 到 master pod）
install -m 0755 cmd/cubefs-mcp/scripts/cubefs-mcp-portforward.sh \
  ~/.local/bin/cubefs-mcp

# 3. 验证 wrapper 找得到二进制
which cubefs-mcp        # → ~/.local/bin/cubefs-mcp
ls -l ~/.local/libexec/cubefs-mcp

cubefs-mcp-portforward.sh 做的事：在指定 K8s 集群里挑一个 cubefs-master-* pod， 起一个 kubectl port-forward，把 :17010 接到本地，再 exec 真正的 Go 二进制。 wrapper 退出时 port-forward 会被 trap 一并杀掉，不会留僵尸。

环境变量

变量必填含义
KUBECONFIG是（wrapper 模式）目标集群的 kubeconfig；切换集群只换这个值
NS否cubefs 命名空间，默认 storage-cfs
PORT否master 监听端口，默认 17010
MCP_BIN否cubefs-mcp Go 二进制路径，默认 ~/.local/libexec/cubefs-mcp
CUBEFS_MASTER_ADDR是（裸二进制模式）完整 URL，例 http://master.cfs.svc:17010；wrapper 会自动设
CUBEFS_AUTH_TOKEN否master 启用了 token 鉴权时填；会作为 Bearer 加到每次请求
LOG否wrapper 内部 port-forward 的日志路径，默认 /tmp/cubefs-mcp-pf.log

不想用 wrapper（例如 master 本就直接可达），跳过 step 2，让客户端配置直接 command: ~/.local/libexec/cubefs-mcp + env.CUBEFS_MASTER_ADDR=http://... 即可——裸二进制不依赖 kubectl。

注册到 LLM 客户端

Claude Code（CLI）

编辑 ~/.config/claude/mcp.json（或项目根 .mcp.json），加一条：

{
  "mcpServers": {
    "cubefs-test-k3d": {
      "command": "/Users/you/.local/bin/cubefs-mcp",
      "env": {
        "KUBECONFIG": "/Users/you/.kube/test-k3d",
        "NS": "storage-cfs",
        "PORT": "17010"
      }
    },
    "cubefs-test-hb": {
      "command": "/Users/you/.local/bin/cubefs-mcp",
      "env": {
        "KUBECONFIG": "/Users/you/.kube/test-hb",
        "NS": "storage-cfs"
      }
    }
  }
}

多环境就靠 server 名字区分（cubefs-test-k3d / cubefs-test-hb / cubefs-prod ...）—— 每个环境一个 KUBECONFIG，Claude Code 会把每个 server 的 34 个工具都注册一遍， 工具名前缀就是 server 名。叫 LLM「在 cubefs-test-k3d 触发 bench rule X」就会路由到对应集群。

Cursor / Cline

schema 完全一致——Cursor 编辑 ~/.cursor/mcp.json，Cline 在 VS Code 设置里搜 cline.mcpServers。 三家客户端共用 MCP 标准，区别只在配置文件位置。

Claude Desktop

编辑 ~/Library/Application Support/Claude/claude_desktop_config.json（macOS），结构同上；改完重启 app。

连通性测试（两步）

注册完，让 LLM 跑这两个工具就能确认链路通：

  1. ping——5s 超时探活，返回 OK 说明 cubefs-mcp 起来了、wrapper 的 port-forward 通了、master 可达。 如果 LLM 报「tool not found」一般是配置没生效，重启客户端。
  2. cluster_health——拉完整集群快照。能正常返回 master leader / 各 node 角色，说明 master REST 正确响应、auth token（如配）有效。

建议在 prompt 里固化一句「先跑 ping 再做别的」，避免 LLM 凭空猜想集群状态。

常见故障排查

现象 1：LLM 看不到 cubefs-mcp 工具

先看客户端的 MCP 日志（Claude Code: ~/.config/claude/logs/mcp-*.log）。最常见两种： wrapper 找不到 Go 二进制（MCP_BIN 路径错），或者 wrapper 抱怨 KUBECONFIG is required—— 在 server 配置的 env 块里加上即可。改完务必重启客户端，MCP server 列表只在启动时加载一次。

现象 2：ping 报 no cubefs-master pod found

wrapper 用 kubectl -n $NS get pod -o name | grep '^pod/cubefs-master-' 找 pod。 三种情况会失败：NS 不对（生产可能不叫 storage-cfs）、master pod 还没起、kubeconfig 没权限 list pod。 先 KUBECONFIG=... kubectl -n storage-cfs get pod 在终端复现一遍。

现象 3：cluster_health 报 401 / 403

master 开了 token 校验，但 server 配置里没塞 CUBEFS_AUTH_TOKEN。 token 找运维要（一般在 master 的 cluster.json / auth_node secret 里）， 在 server 配置的 env 加 CUBEFS_AUTH_TOKEN: "..."，重启客户端。

现象 4：bench_rule_create 报 unknown field

master 用 strict json decoder 拒绝未知字段——大概率是 BenchRule schema 演进了，LLM 拍脑袋写的字段名对不上。 先用 bench_rule_list / bench_rule_get 看一个现存 rule 的字段， 对照 syncnode/spec/bench_rule.go 调整。同样的逻辑适用于 sync_rule_create。

现象 5：调用某工具一直 timeout

cubefs-mcp 内部 master HTTP client 默认是 30s 超时。两种可能： （a）port-forward 半死——看 /tmp/cubefs-mcp-pf.log 是不是写满了 error upgrading connection； （b）master 慢——直接 curl http://127.0.0.1:17010/admin/getCluster 复现， 如果 curl 也慢，问题在 master 本身（leader 选举 / etcd 卡）。重启客户端会重新拉 port-forward，是最快的 workaround。

现象 6：切换集群后还连旧的

wrapper 是子进程，只在启动时读一次 KUBECONFIG。改 server 配置后必须重启客户端； 更稳妥的做法是为每个环境配一个独立的 server 名（见 注册 一节），切环境只换 server 不重启。

边界与不做什么

  • 只暴露 master / syncnode 的 admin API，不包 metanode / datanode 的盘级运维（这些走 cubefs-cli）。 理由：admin 操作是「白名单 + 有审计入口」的，盘级操作风险大也分散，不适合 LLM 直接执行。
  • 所有 D 类（destructive）工具的最终权限在 LLM 客户端——cubefs-mcp 不做二次确认， 客户端（Claude Code / Desktop）会按 MCP 标记弹确认框。生产环境的 server 配置建议另起一个 read-only token， 或者在 MCP 客户端层面禁用 D 类工具。
  • 不替代 dashboard——dashboard 仍是看 task 历史 / live trend 图表 / pod 状态的主入口； cubefs-mcp 更适合「一句话查一组指标 / 一句话触发一个动作 / 批量诊断」这类场景。
  • port-forward wrapper 是开发期/运维期方案。生产长期使用可以把 cubefs-mcp 跑在跳板机上， 让 CUBEFS_MASTER_ADDR 直接指向集群内 master service，绕开 wrapper。
