测试：bench 平台

bench 是 syncnode 自带的分布式压测子系统：master 持久化 BenchRule、按 Parallelism 派发分片到多 syncnode、 实时上报 /metrics/bench 给 dashboard，跑完用 HDR Histogram 做跨节点无损合并。 支持 6 类 backend——fio（POSIX 块 IO）、s3、sdk、mdtest、IOR、pjd-fstest——同一套 rule / task 接口。

  • 核心对象BenchRule（模板） + BenchTask（一次执行）
  • 调度方式master 派发，N 个 syncnode 并行跑 N 个 shard
  • 结果合并HDR Histogram 跨节点无损合并（p99 / p999 不失真）
  • 面向读者性能 / 兼容性 / 容量规划工程师

bench 是什么

为什么 syncnode 里要带一个 bench 平台？因为同一批节点本来就挂了所有 backend：cfs 卷（POSIX）、s3 endpoint、本地盘。 把测试逻辑塞进 syncnode 而不是单独起 fio/IOR Pod，可以直接复用 sync 任务的派发、心跳、状态机、HDR 上报与 dashboard 一致的「rule / task / 进度 / 结果」UI。一份 yaml 既描述同步规则也描述压测规则，没有第二套调度。

它不替代生产前的 SLA 验收（火山自有性能实验室、客户侧 ai-training 压测），而是给 SRE / 开发提供 「随时拉一个 cluster，跑一组对比，看 p99 / 带宽 / 错误率」的最小闭环： 测过的镜像才进生产，回归测试天天跑，故障复盘按 BenchRule 复演。

6 类测试层级

所有层级共用一套 BenchRule / BenchTask，差别只在 storageType 与对应的 stage 配置块。 下表的"触发方式"列出最常用的入口；其余等价。

storageType 典型负载 用来回答 触发方式 结果维度
posix fio（顺序读写 / 随机读写 / RWMix / Mixed 多 size 类） cfs 卷在 4k/64k/1M 各种块大小下的 IOPS / 带宽 / p99 延迟 dashboard「测试管理 → 新建 BenchRule → POSIX fio」 per-stage 吞吐 + IOPS + 延迟分位 + 错误数；Mixed 还按 size class 拆分
s3 put / put_multipart / get / get_range / head / list / delete objectnode 的对象操作延迟 / 长尾 / 并发能力 dashboard 同上选「S3」；或 master POST /benchRule/create op-level HDR Histogram；S1.6 支持 ramp/steady/rampDown + targetIops/targetBwMiBs 限速
sdk 调 cubefs Go SDK 的 PutObject / GetObject 绕过 objectnode 直连 SDK 链路的本身性能（用来对照 s3 path） dashboard / mcp / REST 任意 与 s3 相同；通过对比即可定位 objectnode 是否是瓶颈
mdtest mpirun -n N mdtest（元数据创建 / 查找 / 删除） metanode 在大目录 / 深目录树下的元数据吞吐 BenchRule 配 mdtestStages；sidecar 启动 mpirun creates/sec、stats/sec、removes/sec，按 stage 聚合
ior cubefs-bench-tools sidecar 跑 IOR / mdtest（HPC 标准压测） 跨 syncnode 同步 IO 行为下，cfs 在 IOR 标准用例上的横向数据 BenchRule 配 iorStages，sidecar HTTP 在 127.0.0.1:18000 -O summaryFormat=JSON 透传，sidecar 解析后回写 stage 结果
pjd-fstest POSIX 一致性测试（pjdfstest 全套 8000+ case） cfs 是否对外表现得"像 POSIX"——permission / open / rename / xattr 等覆盖 cubefs-deploy 的 envs/<env>/test/smoke Job + pjd-fstest 镜像 pass / fail 用例数，按子目录分类

BenchRule + BenchTask 模型

BenchRule（持久化在 master 的 rocksdb 里）= 一份压测模板，含 storageType、stages 列表、 Parallelism（shard 数）、可选 SLA、可选 Soak 长跑、可选 CacheDrop / Warmup。 BenchTask（master BenchTaskLedger 里默认 1000 条 LRU）= 一次实际执行， 指向某个 ruleID，被分成 Parallelism 个 shard 派发到 syncnode；每个 shard 跑完上报 BenchShardResult，master 汇总成 BenchTaskRecord.AggregatedStages。

「rule 是模板、task 是一次执行」意味着：改 rule 不影响历史 task；同一 rule 可以 trigger 多次得到多个 task 做对比；rule 被删之后已有 task 仍然可查（直到被 LRU 淘汰）。

任务生命周期

stateDiagram-v2 direction LR [*] --> running: trigger\n创建 BenchTaskRecord running --> shardA: shard 0\n派发到 syncnode running --> shardB: shard 1 running --> shardC: shard N shardA --> aggregating: ShardResult\n上报 shardB --> aggregating shardC --> aggregating aggregating --> succeeded: 全部 done\n+ HDR 合并\n+ SLA 通过 aggregating --> failed: 任一 failed\n或 SLA 不通过 running --> cancelled: cancel\n（仅 running 可取消） failed --> running: retry\n（终态可重试） cancelled --> running: retry succeeded --> [*] failed --> [*] cancelled --> [*] note right of running master 按 Parallelism\n并行派发 N 个 shard\n到不同 syncnode end note

状态字符串来自 master/bench_task_ledger.go：running / succeeded / failed / cancelled。 BenchTaskStatus.IsTerminal() 判定 succeeded/failed/cancelled 为终态，只允许从终态 retry。

3 个典型 BenchRule

示例 1：fio 随机读写（POSIX）

4 个并发 shard，每个跑 fio randrw 60 秒，4k 块；FIODefaults 复用到所有 stage，stage 只覆盖差异字段。 SLA 要求 p99 ≤ 5ms、错误率 ≤ 0.1%。 

name: cfs-randrw-4k
storageType: posix
parallelism: 4
mountPath: /cfs/posix-bench
fioDefaults:
  ioengine: libaio
  iodepth: 32
  numjobs: 4
  bs: 4k
  size: 4G
  runtime: 60
  direct: 1
fioStages:
  - name: randwrite
    rw: randwrite
  - name: randread
    rw: randread
    reuseFiles: true
  - name: randrw-7030
    rw: randrw
    rwmixread: 70
    reuseFiles: true
sla:
  - p99MsMax: 5
    errorRateMax: 0.001
output:
  percentiles: [50, 95, 99, 99.9]

示例 2：IOR 大文件吞吐（HPC）

2 个 shard，每个 shard 在自己的 syncnode 上 fork mpirun 跑 IOR write + read；sidecar 把 IOR 的 JSON summary 回写。mountPath 即 IOR 的工作目录，iorStages[*].targets 留空时 落到 mountPath 下。 

name: cfs-ior-1m-streaming
storageType: ior
parallelism: 2
mountPath: /cfs/posix-bench
sidecarEndpoint: http://127.0.0.1:18000
iorDefaults:
  useMpi: true
  mpiBin: mpirun
  numTasks: 8
  timeoutSec: 600
iorStages:
  - name: ior-write
    tool: ior
    args: ["-w", "-t", "1m", "-b", "16g", "-F", "-i", "1", "-k"]
  - name: ior-read
    tool: ior
    args: ["-r", "-t", "1m", "-b", "16g", "-F", "-i", "1"]
sla:
  - bwMiBsMin: 800
    appliesTo: "ior-*"

示例 3：S3 mixed put + range-get（多 size 类）

单 shard 跑混合负载：90% small put（64KiB） + 10% large put（16MiB），再跑一段 get_range； sizeClass 把延迟拆成 small / large 两条曲线写进 dashboard。S1.6 的 ramp/steady 让前 10s 缓增到 目标 1000 op/s，避免冷启 burst 把 p99 拉花。 

name: s3-mixed-90-10
storageType: s3
parallelism: 1
backendID: bench-objectnode-01
keyPrefix: bench/mixed-90-10/
stages:
  - name: mixed-put
    numjobs: 16
    runtime: 120
    objectSize:
      fixed: 65536
    ops:
      - type: put
        weight: 9
        size_class: small
      - type: put
        weight: 1
        size_class: large
        part_size_mib: 16
    control:
      rampUpSec: 10
      steadySec: 100
      rampDownSec: 10
      targetIops: 1000
  - name: range-get
    numjobs: 8
    runtime: 60
    objectSize:
      fixed: 16777216
    ops:
      - type: get_range
        weight: 1
        range_offset_bytes: 0
        range_size_bytes: 65536
sla:
  - p99MsMax: 50
    appliesTo: mixed-put
output:
  percentiles: [50, 95, 99, 99.9]

结果观测：实时 + 终态

bench 暴露两条独立的观测口子：

  • 实时趋势 /metrics/bench：syncnode 在 :17030 暴露 Prometheus 端点（独立 BenchRegistry，不和 syncnode 自身指标混在 /metrics）。 fio 路径每秒产出 fio_interval_throughput_mibs / fio_interval_iops / fio_interval_latency_us_*， s3 / sdk 路径产出 op-level histogram。dashboard 直接抓这个端点画实时趋势图。
  • 终态结果 GET /benchTask/get?id=<taskID>：master 返回 BenchTaskRecord，含每个 shard 的 BenchShardResult.Stages（per-stage 吞吐 / IOPS / p50-p99.9） 和父任务的 AggregatedStages（跨节点 HDR 合并后的 p99 / p999，不失真）。

HDR 合并是关键：传统做法把多节点的 p99 取均值会丢长尾，bench 做法是每个 shard 上报 gzip+base64 的 HDR snapshot（BenchStageResult.HDRBuckets），master 用 syncnode/hist.MergeSnapshots 合并再计算分位，得到的就是「这个 cluster 的 p99」而不是「平均节点的 p99」。

bench-mount 多节点共享

POSIX / IOR / mdtest 都需要每个 syncnode 看到同一个 cfs 卷的同一目录（否则 IOR 跨节点协调不了文件）。 cubefs-deploy 通过 bench_mount_pvc_name + bench_mount_storage_class = cfs-sc 建一个 RWM（ReadWriteMany）PVC，挂到每个 syncnode 的 /cfs/posix-bench。

关键限制（必看）：

  • 必须 RWM：不能用 RWO，否则只有一个节点能挂上，IOR 跨节点直接失败。
  • 升级必须走 OnDelete：cubefs-csi 在多节点同时 NodeStage 同一个 RWM volume 时会卡 mount --bind exit 32，所以 syncnode 用 OnDelete 策略，升级要串行手 delete。 详见部署页 OnDelete SOP。
  • 不要在 bench-mount 里塞业务数据：它是「压测专用工作目录」，rule 配的 fio cleanupAfterDone 与 ior -k（keep）都按这个假设设计。
  • test-k3d 例外：单节点测试时 bench_mount_pvc_name = ""，fio 只能跑 parallelism = 1（默认 max_concurrent_tasks=1，maxQueueSize=2 故意压小用来验证取消队列）。

常见故障排查

现象 1：BenchRule create 报 backendEndpoint required

storageType = s3 / sdk 强制需要 backendID（rule 持久化时校验）+ backendEndpoint（dispatch 时由 dashboard / master 从 backendID 解析后填入）。 POSIX / mdtest / IOR 只读 mountPath，不需要 backend。 对应代码 spec.BenchStorageType.RequiresBackendEndpoint()，rule 与 trigger 两端都校验。

现象 2：fio 跑出来 p99 比预期高 10x

90% 是冷启 burst：worker 一开 16 并发同时压上去，cfs 客户端读 inode/extents 元数据全没缓存。 用 control.rampUpSec / steadySec / rampDownSec 缓增到目标，或挂 warmup 跑一段 不计入结果的预热（subsetRatio 0.1 = 只覆盖前 10% 的文件集）。 另一半场景是机器 page cache 没清干净——多 stage 串跑时打开 cacheDrop.enabled: true + betweenStages: true。

现象 3：IOR sidecar HTTP 500 / 拒绝连接

sidecar 容器没起来、或者 sidecar 镜像缺少 /usr/local/bin/ior。 kubectl -n storage-cfs logs <pod> -c bench-tools 看 sidecar 日志； 手动 kubectl exec ... -c bench-tools -- which ior mpirun 验证二进制。 sidecarEndpoint 默认空字符串走 http://127.0.0.1:18000， 测试环境覆盖时一定要写带 scheme 的完整 URL。

现象 4：bench task 一直 running 不动 / 一个 shard 卡死

先看 GET /benchTask/get?id=<taskID> 的 shards： 如果某个 shard 的 nodeAddr 的 syncnode pod 已经不在了（节点维护、被驱逐）， master 的 orphan 扫描会在心跳 miss 后把 shard 标 failed。 不要直接 kill pod 想"加速"：bench 任务没有断点续跑（除非配 soak.resumeFromCheckpoint）， kill 后只能 retry 整个任务。正确做法：POST /benchTask/cancel?id=... 让任务进 cancelled 终态， 再 retry。

现象 5：SLA 一直 fail 且 reasons 写 stage not matched

BenchSLA.appliesTo 用 path.Match 的 glob 语法， "randwrite-*" 不会匹配 "randwrite_4k"（下划线不是 -）。 SLA 设计上"匹配 0 个 stage = 用户大概率拼错了"，所以会直接 fail，而不是静默通过。 修：把 appliesTo 改成准确的 stage 名或正确的 glob。

现象 6：HDR p99 比每个 shard 的 p99 都大很多

这是正常的：每个 shard 的 p99 是该 shard 自己 1/N 流量下的 p99； HDR 合并后看的是 整个 cluster 全量请求的 p99，long tail 自然更长。 如果反过来 HDR p99 比单 shard 还小，说明 HDRBuckets 上报缺失（fio / mdtest 路径不上报 HDR， fallback 到加权平均），这时 dashboard 的 p99 是估算值而非真实分位——同步 / 兼容性测试场景接受， SLA 严格场景应改用 storageType: s3 或 sdk 走 HDR 路径。
