架构与流程

读完本页可以回答：CubeFS Sync & Bench 由哪几个角色构成，他们之间怎么协作，一次同步或一次压测从下发到完成中间经过了哪些环节，数据完整性怎么保证。

  • 覆盖角色master · syncnode · dashboard · bench
  • 流程图整体架构 / sync 时序 / bench 时序 / 数据流
  • 面向读者初次接入 / 排障 / 集成开发者

四个角色

CubeFS Sync & Bench 体系挂在 CubeFS 主集群之上，复用 master 控制面和 metanode / datanode 数据面，额外引入两类组件—— syncnode（执行）和 dashboard（控制台），以及一个跑在 syncnode pod 里的 bench sidecar。

  • master：CubeFS 控制面主节点，扩展承担 sync / bench 规则与任务的持久化、调度入口、syncnode 心跳。三主 raft。
  • syncnode：独立 DaemonSet（cfs-server -c sync.json，role=sync），承担 sync / load / check / bench / move 五类任务的实际执行。本地用 BoltDB 存 InProgressStore 以支持断点续传。
  • dashboard：Vue + Go 后端的运维 UI，覆盖卷管理、节点管理、Sync / Bench 规则与任务、测试分析（Prometheus 代理），以及 POSIX 合规独立菜单。后端有自己的 MySQL（独立于 master raft）。
  • bench sidecar：syncnode pod 内的辅助容器 cubefs-bench-tools，封装 fio / IOR / mdtest / OpenMPI / tini，对外暴露 HTTP runner 127.0.0.1:18000。主容器只负责调度，重 IO 一律走 sidecar。

四者之间没有循环依赖：dashboard 依赖 master REST；master 依赖 syncnode 心跳；syncnode 依赖 master 派发；bench sidecar 是 syncnode 进程的本地子系统。这意味着 master 重启不会丢任务（已落 raft），syncnode 重启不会丢进度（已落 BoltDB），dashboard 重启完全不影响数据面。

Bench 任务生命周期

Bench 任务复用了与 sync 相同的派发与心跳通道，但执行端不是『搬文件』，而是把 fio / IOR / mdtest 跑起来并把结果以 HDR histogram 形式回流。 跨 shard 的结果用 HDR histogram 合并，避免简单加和带来的失真；多个 shard 在 ramp-up 阶段通过 Consul KV barrier 同步开跑。

数据完整性流

使用者最容易忽略但最影响生产可用的就是数据完整性。Sync 体系把校验放进传输管道里同步计算，而不是落盘后再回读； type=move 类型的规则强制走 strong 模式，否则 executor 拒绝执行删源。

关键设计选择速览

  • master 持久化 sync / bench rule + task：避免 syncnode 重启或扩缩容时丢规则。
  • syncnode 本地 BoltDB：保存断点续传偏移；本地状态独立于 master，无需高频回写 raft。
  • ShardCount 与 Parallelism 解耦：前者控制规则分发到多少个 syncnode，后者控制单进程内并发；两个旋钮不再混淆（见 同步 / 调度参数）。
  • bench HDR histogram 合并：跨 shard 真合并而不是平均，p99 / p999 不会被掩盖。
  • RWM PVC 共享 bench-mount：让 IOR / mdtest 这种要求多 rank 看同一目录的工具可用；与之配套的就是 syncnode 必须走 OnDelete 升级（见 部署 / OnDelete SOP）。
  • checksum 同步计算：写盘的同时算 sha256，不做事后回读；落地速度最快、内存占用可控。
